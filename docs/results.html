Test results

Before trusting an agent with money, test it on cases where the right answer is known, and compare it with what rules alone would do. A separate AI instance played the agent: it saw only the policy and the case inputs, never the answers. Two rule sets ran on the same cases: a naive one (exact matches and keywords) and a fair one, written from the policy by a competent engineer without a model.

Read this before trusting the numbers. The three published sets (190 cases) were written by AI from the same policy, so they test whether the agent follows its rules on clean, labelled cases. A fair rule set written from the policy matches the agent on all 190, which is the honest finding: where the input is structured and the policy is written down, rules are enough, and the product uses rules there. The model earns its place on what these cases cannot hold: real decline text, real email threads in other languages, invoice PDFs and bank narrations. The fresh set (36 cases, written after the build without the keys) is the first look at that gap: the agent disagreed with the key once, the fair rules twice. A pilot with real exporters and a holdout group is the real test.

How the test was run

  1. Policy: sections 1 to 10 of the agent's rulebook were the only instruction the model received (v1 for the standard and hard sets, v1.1 with the untrusted-content section for the safety and fresh sets).
  2. Standard set (120 cases): generated by a seeded script with an answer key: 60 payments to match, 30 declined payments, 30 client replies, including traps such as "We dispute nothing, payment is scheduled for the 15th".
  3. Hard set (60 cases): written by a separate AI instance told to break the agent: garbled payer names, look-alike clients, bank charges at the limit, forwarded email chains, sarcasm, replies in German, French, Spanish and Dutch.
  4. Safety set (10 cases): instructions hidden in client emails and payment references, a look-alike email domain, a fake verification link, plus normal controls.
  5. Fresh set (36 cases): written on 12 October by the second-judge pass with only the policy in view, keyed by applying the policy literally, then played blind by another fresh instance.
  6. Blind runs: a fresh AI instance received only the policy and the inputs, and wrote one decision per case with its confidence and reason.
  7. Two rule baselines: naive (exact invoice number and amount, or exact client name and amount; keywords for declines and replies) and fair (fuzzy invoice numbers, bank-charge tolerance, sums, aliases, a decline-code table, phrase rules with negation and a small multilingual vocabulary).
  8. Scoring: a script compares all three with the answer keys. Inputs, answer keys, outputs and the scoring code are published with the prototype.
