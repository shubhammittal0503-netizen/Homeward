# Homeward: AI build log

Homeward is a concept agent, imagined inside Razorpay's Agent Studio, for small Indian services exporters paid through Razorpay. It treats the invoice as the unit of work: each morning it lists the overseas money that is not home, says why, and prepares the fix for the owner to approve. Entry by Shubham Mittal (ISB PGP 2027) for the Razorpay AI x PM Build Challenge, Track 2, October 2026. Every merchant, client, invoice and amount in the prototype is made up; nothing here comes from any employer, and there are no keys or private data in the repository.

## AI tools and models used
- Claude in Cowork (the Claude desktop app), two sessions between 8 and 12 October 2026. The first was configured as claude-opus-5-5 and did the research, the problem choice, the prototype build and the first blind tests. The second was configured as claude-fable-5-1 and ran an independent second-judge pass: scoring the entry against the rubric, redesigning the site, writing a fresh adversarial test set, and fixing what it found. In both, the model serving a given turn can differ from the configured one, and the session cannot see which.
- Subagents launched from those sessions, each a fresh instance with a written brief: parallel research agents; a blind "agent" instance that saw only the policy and the case inputs; an adversarial test writer (the 60-case hard set and the 10-case safety set); three judge personas (an AI screener reading text only, a Razorpay PM, a time-poor judge); a fair-baseline author that saw the policy and the inputs but not the answer keys.
- An outside review by ChatGPT (Codex) on 12 October, reading the repository from disk, which scored the entry and found eight defects that were then fixed.
- Tools: Python 3 standard library for the site generator, the test generator and the scorers; Playwright with Chromium for QA and screenshots; web search and fetch for sources (RBI, DGFT, Razorpay docs and blogs, press); GitHub Pages for hosting. No Razorpay API, no live model call in the published site, no AI voice, no image generation.

## key prompts, workflows, or agent setup
- **The agent is a policy, not a prompt.** `agent/policy.md` is the only instruction the model received in the blind tests: version 1 (sections 1 to 9) for the standard and hard sets, version 1.1 (section 10, untrusted content) for the safety and fresh sets. Version 1.2 added a holiday clause, section 11 (what learning may change) and section 12 (clarifications the fresh set exposed) after all runs; it changes no test decision. Two lines from it: "Confidence threshold 0.80. Below it, ask the owner. Never guess with money." and "If the owner says no to a suggestion, it is not suggested again for 30 days."
- **Blind test workflow.** `tools/make_tests.py` writes the 120 standard cases and keys from a seed. A separate instance wrote the hard and safety cases to break the agent. Another instance played the agent with only the policy and the inputs, returning a decision, the invoices, a confidence and a one-line reason per case. `tools/score.py` compares the stored outputs with the keys and with two rule baselines: `tools/baseline.py` (naive: exact matches and keywords) and `tools/baseline_fair.py` (fuzzy invoice numbers, bank-charge caps, sums, aliases, a decline-code table, phrase rules; written by a separate instance from the policy without the keys; it runs without a model).
- **The fair-baseline brief, in substance:** write the rule set a competent engineer would write from this policy without a model; read the policy and the case inputs; do not read the answer keys, the agent outputs or the generator.
- **The judge-persona brief, abridged:** "You read only text: the HTML a server sends (no JavaScript), raw markdown, and extracted text. You score criterion by criterion, quote the evidence you rely on, and dock claims that are not backed by evidence."
- **The build.** Static HTML generated by `tools/build_site.py` from `data/demo.json` and the test outputs; hand-written CSS and one small script; `tools/qa.py` checks links, the concept label on every page, no dashes, British spelling, no sideways scroll at 390 px, text intact with JavaScript off, and the approve and reset flows.
- **The second-judge workflow.** A written brief asked a fresh session to read everything, score the entry, run three judge personas, list holes, propose design directions as mockups, and only then build in an agreed order, keeping a change log, a fact register with a source and date for every number, and SHA-256 checks on every file.

## one AI output you rejected, corrected, or significantly improved, and why
**Fifteen months or nine.** Razorpay's blog of 8 September 2026 said export proceeds must be realised within fifteen months. The RBI's regulation said nine. The product followed the RBI and showed nine-month clocks. The second-judge pass re-read the RBI page and found why the two disagreed: the regulation was amended on 22 September 2026 (FEMA 23(R)/(1)/2026-RB, gazetted 24 September), substituting "nine months" for "fifteen months". The blog was right when written and stale afterwards. The Export forms page now quotes the amended regulation with its date, and every rule on the site carries a source and the date it was checked.

**Also corrected:** the first blind test came back 120 of 120, which looked implausible; a separate instance then wrote 60 hard and 10 safety cases, and after the build a second judge wrote 36 more without the keys. The agent then disagreed with a key once. More important, a fair rule set written from the policy matched the agent on every published case, which changed the claim: the published sets test whether the agent follows its rules; the model's margin shows only on the fresh set and must be measured on real text. The site, the README and this log say so. Other corrections: a page the QA passed and a judge failed (Controls unreadable on a phone; fixed with a one-column layout and a new check); a route step labelled AI when the rule picks the route; a US public holiday the schedule ignored; "the bank issues the eBRC" (the exporter generates it on the DGFT portal); a light-theme text colour at 4.44:1, under AA.

## known limitations, risks, or verification steps
- **Concept, not integration.** No Razorpay API and no live model call in the published site. The demo morning's cases and the AI reasoning shown on them were authored for the demo (`tools/demo_data.py`); the real, stored model outputs are the blind-test files under `eval/outputs/`, scored against the keys. Razorpay has no view of a bank's EDF status today; the design assumes an EDF-number field the partner bank confirms.
- **Synthetic evidence.** Every merchant and case is made up; the merchant voice is public reviews and press, not interviews. The sizing is a scenario with stated assumptions (₹88 a dollar; half the inflow by card; 15% failing; 35% won back).
- **Tests measure policy compliance.** The 190 published cases were written by AI from the same policy, and a fair rule set matches the agent on all of them. The fresh set (36 cases, written after the build without the keys, by the same assistant that judged the entry) is the first look at the model's margin: one disagreement against two. Confidence is the model's own estimate, not a measured error rate; the scorer compares decisions with the keys and does not enforce the 0.80 threshold itself.
- **Regulatory flux.** The EDF regime is two weeks old; the RBI's FAQs were not published as of 12 October; purpose codes for design work are disputed, so the agent asks. Rules carry their source and date on the site.
- **Risks the design addresses, not removes:** wrong matches (ask under 0.80; a link is unlinked before capture and corrected through Razorpay support and the bank after it); over-contact (two reminders, client hours and holidays, do-not-contact, a no is a no); manipulation through replies and references (treated as data, never instructions; tested in the safety and fresh sets).
- **Verification steps:** every rule re-read at source with the date recorded; every rupee total re-added from the data; the build reproduced on a Mac with Python 3.10 and parsed as Python 3.9 syntax; every committed file checked by SHA-256; QA on all 33 pages; screenshots at 1280 and 390 px in light and dark; contrast computed for every colour pair; an outside review of the repository before submission.
